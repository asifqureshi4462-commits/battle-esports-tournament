2.  Home

HOME DASHBOARD - App logo/name and notification indicator. - User
greeting and profile shortcut. - Wallet balance and coin balance,
sourced from backend. - Featured/upcoming tournaments. - Live
tournaments and recently completed tournaments. - Announcements and
important notices. - Quick actions: Browse Tournaments, My Matches, Add
Cash, Withdraw, Support. - Never show hardcoded balances or fake
tournament data in production.

TOURNAMENTS SECTION - Tabs/filters: All, Upcoming, Live, Completed, My
Joined. - Search and filter by game, mode, entry fee, date, and
status. - Tournament cards show game/title, banner, match date/time with
timezone, entry fee, prize pool, mode, map, slots filled/total, and
status. - Tournament details screen includes description, rules,
eligibility, registration deadline, schedule, entry fee, prize
distribution, participant limit, and support contact. - Join tournament
confirmation dialog shows the exact fee and rules. - Validate
eligibility, available wallet funds, registration window, participant
limit, and duplicate registration on the backend. - Deduct entry fee
only through an atomic backend transaction; if registration fails, do
not charge or safely refund. - Show registration result and a unique
registration record. - Prevent duplicate joins even if the user taps
repeatedly or has network retries. - Clearly show room ID/password only
to authorized registered participants and only when the admin releases
them. - Show match result and prize information after admin publication.

MY MATCHES - Tabs: Upcoming, Live, Completed, Cancelled. - Show joined
tournaments, registration status, match time, rules, room details when
authorized, and result. - Notify users when schedule, room details, or
results change. - Do not expose private match credentials to
nonparticipants.

WALLET SECTION - Show available balance, reserved/pending amount if
applicable, and transaction history. - Transaction types: Deposit, Entry
Fee, Prize, Refund, Withdrawal, Adjustment. - Each transaction shows ID,
amount, status, date/time, and description. - Wallet balance must be
computed/updated by trusted backend operations, never by trusting
client-submitted balances. - Maintain an auditable ledger. Prevent
duplicate credits/deductions and negative balances unless explicitly
allowed by documented rules. - Never erase historical transactions when
status changes.

ADD CASH / DEPOSIT - User enters or selects amount; validate allowed
minimum/maximum values on the backend. - Create a unique deposit/order
ID on the backend. - Use an eligible payment gateway/merchant service
that supports the chosen UPI flow and server-side payment
verification. - Display a provider-generated payment page/QR for the
exact order amount where supported. - Verify actual payment through
authenticated provider API and/or cryptographically verified webhooks. -
Match verified payment to user, order ID, amount, currency, merchant,
and provider transaction reference. - Credit wallet exactly once only
after confirmed payment success. - Handle pending, failed, expired,
cancelled, and duplicate webhook cases. - A screenshot, user-entered
UTR, or “I Have Paid” button is not proof of payment. - If no payment
provider credentials are configured, show a clearly marked
configuration-required state; never fake successful deposits. - Admin
may review deposits, but manual approval must not be represented as
independent bank/payment verification unless it truly was verified.

DEPOSIT STATUS MANAGEMENT Use consistent canonical statuses such as
pending, verification_pending, successful, failed, rejected, expired. If
the product needs only three admin tabs, map the canonical statuses
consistently to Pending, Successful, and Rejected while retaining
accurate underlying payment state. - Pending list shows only records
matching the configured pending/review states. - Successful list shows
only successful records. - Rejected list shows only rejected records. -
On status change, update the database record using its unique ID and
await confirmation before moving it in the UI. - Refresh/reopen must not
put a successful/rejected request back in Pending. - Avoid duplicate
records and duplicate wallet credits. - Show useful failure details if
the database write fails; do not hide a record locally as if saved. -
Use real-time listeners correctly if already supported.

WITHDRAWALS - User can securely add/edit their own payout UPI ID or
supported payout details. - Validate payout details and withdrawal
amount on the server. - Display available balance and minimum/maximum
withdrawal rules. - Create a unique withdrawal request ID. - Statuses:
Pending, Processing, Successful, Rejected. - Admin view must show user
ID/username, amount, payout destination as permitted, request ID, and
timestamps. - Reserve/deduct funds according to a clearly documented
transactional policy. - On rejection, release/refund reserved funds
exactly once. - Mark a withdrawal Successful only when it has actually
been paid or a permitted, clearly documented manual payout has been
confirmed. - Prevent duplicate withdrawals and duplicate refunds. -
Display the latest status to the user and preserve withdrawal history.

PROFILE & ACCOUNT SETTINGS - User profile, username, avatar, email/phone
where applicable, and account details. - Change password and Forgot
Password using verified email/phone and the existing authentication
provider. - Secure logout and session handling. - Users may update only
fields they are authorized to edit. - Preserve wallet, matches,
transactions, and history when changing a password. - Never store
passwords in plain text.

NOTIFICATIONS - In-app notifications for successful/failed deposit
verification, withdrawal status, tournament join, schedule changes, room
details availability, match results, prizes, and admin announcements. -
Notifications must be tied to authenticated users and must not expose
another user’s data. - Avoid sending duplicate notifications for the
same event.

CUSTOMER CARE / SUPPORT - User can submit a support ticket with
category, subject, message, optional safe attachment if supported, and
creation time. - User can view their own tickets and replies. - Admin
can view and reply to tickets, assign status (Open, In Progress,
Resolved), and see user/request IDs. - Validate inputs and restrict
users to their own tickets.
